# 0051. The seed has four users in two organizations, the sign-in page lists them in development, and the account forms wait for the circuit

Status: accepted. Extends ADR 0050 (demo seed) and amends ADR 0042 (account pages stay interactive). Applies the reference architecture's demo-data rule (through the public interfaces, deterministic, idempotent, namespaced, development only), P5 (tokens never reach the browser) and P13 (a defect only a browser sees is tested in a browser).

## Context

The owner asked that after any local start they can test at once with ready-made users, and that the three roles and cross-workspace isolation can be tried by hand. ADR 0050 seeded an owner and a member of one organization. The sign-in page gave no hint which logins exist. The last PR also found that typing or clicking on an account page very early is lost: the page is interactive (ADR 0042), so the circuit's first render replaces the prerendered form.

## Decisions

1. **Four users, two organizations.** `owner@dev.test` (Owner), `admin@dev.test` (Admin) and `member@dev.test` (Member) belong to `Dev Workspace`; `other@dev.test` founds and owns `Other Workspace`, with one board, `Demo: Other workspace board`. The owner invites the admin and the member with their role through authservice's invite call; each accepts. The roles are the ones authservice puts in `organization:{id}:role` and that the web app reads (`Membership`: invitations are for Owner and Admin). **No user is in both organizations**: the web app uses the single organization in the token (ADR 0024), and `WorkspaceClaims` refuses a token with two.
2. **The seed stays idempotent and namespaced.** Per workspace it signs everyone in, finds the organization by name, invites only users whose token lacks it, and re-signs everyone in afterwards (the founder's own token predates the organization, so this is needed even when nobody is invited; a unit test caught it). Invitation tokens are told apart by which the seed has already used, since authservice prints one per invitation. `--reset` still removes only `Demo: ` boards, now in both workspaces. `Seed__InvitationToken` holds one token, so it serves a single invitation; the Docker socket and the log file serve any number.
3. **A development-only hint on the sign-in page.** It lists the four logins (email, role, organization) and the published password, and a click fills the form without submitting. It shows only when the web app runs in Development **and** `Seed:Enabled` is true. The switch is the seed's own: the AppHost passes `Seed__Enabled` to the web resource (true only when it runs the seed, so false outside Development) and compose passes `${SEED_ENABLED:-true}`. Unset means hidden, so a missing setting never shows credentials. The web app restates the values (`MiroClone.Web.Account.DemoLogins`) because it references no other project; the browser journeys sign in through the hint on a seeded estate, which proves the two lists agree. Nothing new reaches the browser except the published development values, and tokens stay on the server.
4. **The account forms wait for the circuit.** Every account form's controls sit in `InteractiveFieldset`, a `fieldset` that is `disabled` while `RendererInfo.IsInteractive` is false. The prerendered form therefore takes no input, so nothing typed or clicked can be lost when the circuit replaces it; the interactive render enables it. This fixes the cause, not the timing: the journey's loop that refilled the form and repeated the click is gone, and `SignInAsync` waits for the form to be enabled, fills once and clicks once. One retry remains, for a different failure that the old loop had been absorbing: on the CI estates (compose and the AppHost alike) an authservice call occasionally stalls for the web's whole 30 s request budget and the page answers "The account service is not reachable". The helper repeats the sign-in, at most three attempts, only for that answer, and prints each occurrence; every other outcome fails at once. The stall is not explained and not caused by this change (it showed on a journey that predates it); `AuthorityClient` now logs the exception behind that message so the next occurrence leaves a cause. A pin test requires the fieldset in every account form. The cost: without a circuit (script blocked, WebSocket and long polling both unavailable) the forms stay disabled, where ADR 0042 said "the circuit is not needed to sign in". The app is interactive-only and needs the circuit for everything after sign-in, so that case was never usable; the alternative (static account pages) was rejected in ADR 0042 and still is. The dashboard's "new board" click-repeat in the journeys is a different page and is left as it is.

## Consequences

- `scripts/verify-seed.sh` checks four logins with their role claims, the boards each sees, the shapes of the first board, and a 404 both ways between the workspaces. The seed's log table, the README and `docs/AUTH.md` list the four logins.
- The seed's database footprint is unchanged: still the public APIs only. A kept authservice database from before this change has the owner and the member already; a re-run adds the admin and the other user.
- `Seed__Enabled` is now a web setting too; `ComposeParityTests` and `SeedWiringTests` pin that both start paths set it from the same switch.
